# commit: 변경사항 분석 및 자동 커밋

현재 git 저장소의 변경사항을 분석하여 컨벤션에 맞는 커밋 메시지를 작성하고, **별도 승인 절차 없이** 바로 커밋한다. 이 스킬이 트리거된 것 자체가 커밋 수행에 대한 사용자 승인이다.

## 워크플로우

### Step 1: 변경사항 분석

- `git status`로 전체 변경 파일(staged/unstaged/untracked)을 확인한다.
- `git diff`(unstaged)와 `git diff --staged`(staged)로 실제 변경 내용을 확인한다.
- 저장소 루트의 `AGENTS.md`/`CLAUDE.md`에 커밋 메시지 컨벤션이 명시돼 있으면 그것을 우선 따른다.
- `git log --oneline -20`으로 기존 커밋 메시지 스타일(타입 표기, 언어, 길이 등)을 참고한다. 커밋 이력이 없으면 아래 기본 컨벤션을 사용한다.

### Step 2: 논리적 단위로 분류

- 변경사항이 서로 다른 관심사(기능 추가, 버그 수정, 리팩터링 등)를 포함하면 파일/영역 단위로 그룹화한다.
- 하나의 커밋으로 묶을지 여러 커밋으로 나눌지는 diff 내용을 근거로 스스로 판단해서 결정한다(사용자에게 묻지 않는다).
- 관련 없어 보이는 변경(실험적 코드, 임시 디버그 로그 등)도 명백히 실수로 남은 것이 아닌 이상 판단해서 포함 여부를 결정하고 진행한다.

### Step 3: 한국어 커밋 메시지 작성

- 형식: `type: 요약` — 한 줄, 명령형, 간결하게(72자 이내 권장).
- 타입: `feat`(기능 추가) / `fix`(버그 수정) / `refactor`(동작 변경 없는 구조 개선) / `chore`(빌드·설정·잡무) / `docs`(문서) / `test`(테스트) / `style`(포맷팅) / `perf`(성능) 중 변경 성격에 맞는 것을 선택한다.
- 본문이 필요하면(변경 이유가 코드만으로 드러나지 않는 경우) 빈 줄 다음에 "왜" 위주로 작성한다. 무엇을 바꿨는지는 diff로 알 수 있으므로 반복하지 않는다.
- 여러 커밋으로 나누는 경우 각 커밋마다 독립적으로 의미가 통하는 메시지를 작성한다.

### Step 4: 자동 커밋

- 승인을 묻지 않고 바로 진행한다.
  1. 커밋 단위별로 관련 파일만 `git add`한다(파일명을 명시해서 추가하고, `git add -A`/`git add .`는 사용하지 않는다).
  2. `git commit -m`으로 커밋한다(메시지는 heredoc으로 전달해 포맷을 보존한다).
  3. 커밋 후 `git status`/`git log -1`로 결과를 확인해 사용자에게 결과(커밋 해시, 메시지, 포함된 파일)를 보고한다.
- 단, 아래 "안전 규칙"의 예외(민감 파일 발견 등)에 해당하면 그 항목만 자동 진행을 멈추고 사용자에게 확인한다.

## 안전 규칙

- **파일 단위 스테이징만 사용한다.** `git add -A`, `git add .` 등 광범위한 스테이징 금지.
- 스테이징 대상에 `.env`, `credentials.json` 등 민감해 보이는 파일이 있으면 내용을 확인하고 사용자에게 경고한 뒤 진행 여부를 확인받는다.
- `git reset --hard`, `git push --force`, `git clean` 등 파괴적 명령은 이 스킬 범위에 포함하지 않는다.
- `--no-verify`, `--no-gpg-sign` 등 훅/서명 우회 옵션은 사용자가 명시적으로 요청하지 않는 한 사용하지 않는다.
- 커밋 메시지 마지막에 붙여야 할 attribution 지침(예: `Co-Authored-By`)이 대화 컨텍스트에 있으면 그대로 포함한다.
- 이미 커밋되지 않은 다른 작업(관련 없는 변경)을 실수로 포함하지 않도록, 커밋 직전 최종적으로 스테이징된 diff를 한 번 더 확인한다.

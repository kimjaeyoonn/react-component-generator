# TDD Rule

> **이 규칙은 Rigid다 — 상황에 맞게 변형하지 마라.** "이번엔 예외"라는 판단이 들면, 그 판단 자체가 변명이다. 아래 변명 차단표를 먼저 확인하라.

## 0. 우선순위 (Fallback 조항)

이 파일은 **기본값(fallback)** 이다. 프로젝트 루트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 명시되어 있으면 **그 규칙이 이 파일보다 우선**한다. 프로젝트별 규칙이 없거나 침묵하는 부분에 한해 이 파일을 적용한다.

## 1. 적용 기준

### TDD를 반드시 적용해야 하는 대상

- **비즈니스 로직** (도메인 규칙, 계산, 상태 전이)
- **API** (엔드포인트 핸들러, 요청/응답 처리, 에러 케이스)
- **유틸 함수** (순수 함수, 데이터 변환, 파서/포매터)
- **버그 수정** (재현 테스트 없이 고치지 마라 — 재발 방지의 유일한 증거)

### TDD가 불필요한 대상

- **타입 정의** (interface, type alias)
- **설정 파일** (`vite.config.ts`, `eslint.config.js`, `tsconfig*.json` 등)
- **순수 UI** (마크업/스타일만 있고 로직이 없는 프레젠테이셔널 컴포넌트)
- **SQL** (마이그레이션, 스키마 정의)

판단이 애매하면: "이 코드가 잘못된 값을 반환하거나 잘못된 상태를 만들 수 있는가?"를 물어라. 그렇다면 로직이므로 적용 대상이다.

## 2. RED-GREEN-REFACTOR 사이클

### RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 묶지 마라.
- 테스트를 작성한 뒤 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 테스트는 존재하지 않는 것과 같다.
- 실패 이유는 반드시 **"기능 미구현"**이어야 한다. 문법 오류, import 누락, 오타로 인한 실패는 RED가 아니다 — 고치고 다시 실행하라.

### GREEN

- **테스트를 통과시키는 최소한의 코드만 작성**한다. YAGNI — 지금 요구되지 않는 조건 분기, 파라미터, 확장 포인트를 추가하지 마라.
- 신규 테스트와 **기존 테스트가 모두 통과**하는지 확인한다. 하나라도 깨지면 GREEN이 아니다.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출을 수행한다.
- **테스트는 계속 green을 유지**해야 한다. 리팩터링 중 테스트를 고치지 마라 — 테스트가 깨지면 리팩터링을 되돌려라.
- **새로운 동작을 추가하지 마라.** REFACTOR 단계에서 기능이 늘어났다면 그것은 REFACTOR가 아니라 미승인 GREEN이다.

### 반복

REFACTOR가 끝나면 다음 동작에 대한 **RED로 돌아간다.** 사이클을 건너뛰고 여러 동작을 한 번에 구현하지 마라.

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다는 것을 발견하면, **그 코드를 삭제**하고 RED부터 다시 시작한다.
- **"참고용"으로 남겨두는 것도 금지**한다. 주석 처리, 별도 브랜치 보관, `_old` 파일명 등 어떤 형태로든 우회 보존하지 마라.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| 너무 단순해서 테스트 불필요 | 단순한 코드일수록 테스트 작성 비용도 낮다. "단순함"은 생략의 이유가 아니라 테스트가 30초 만에 끝난다는 뜻이다. |
| 나중에 추가하겠다 | 나중은 오지 않는다. 지금 GREEN이 된 코드는 테스트 없이 이미 "완료"로 취급되어 우선순위에서 밀린다. |
| 시간이 없다 | 테스트 없이 짠 코드의 디버깅 시간이 테스트 작성 시간보다 항상 길다. 지금 아끼는 시간은 나중에 이자를 붙여 갚는다. |
| 삭제하면 낭비다 | 검증되지 않은 코드는 자산이 아니라 부채다. 순서를 어긴 코드를 남겨두면 "테스트가 코드를 따라간 것"이 되어 RED의 의미가 사라진다. |
| 프로토타입이다 | 프로토타입은 실제 코드베이스에 커밋되는 순간 프로덕션 코드가 된다. 버릴 것이면 별도 스크래치 공간에서 하고, 커밋하지 마라. |
